# S-7 — Upload Existing Audio

## 1. Problem

Users need a way to share audio files they already have without recording them again.

Evidence E-8 and E-16 describe users accessing and sharing existing audio. Assumption A-4 extends this behavior to uploading short audio clips within Yappify.

Story S-7: As an audio creator, I want to upload an existing audio file so that I can share audio I already have without recording it again.

## 2. Scope

- Allow users to select an existing audio file from their device.
- Validate the file's format and duration.
- Reject files that do not satisfy the configured requirements.
- Display successfully uploaded audio as a playable, unpublished clip.

## 3. Non-goals

- This feature does not edit or trim uploaded audio.
- This feature does not automatically publish or share uploaded files.
- This feature does not convert unsupported audio formats.

## 4. Interface

Proposed TypeScript interface:

```typescript
type UploadResult = {
  audio: Blob;
  durationSeconds: number;
  mimeType: string;
  status: "unpublished";
};

async function uploadAudio(
  file: File
): Promise<UploadResult>;
```

Possible errors:

- UnsupportedFormatError: The file's format is not permitted.
- DurationLimitError: The audio duration exceeds MAX_CLIP_DURATION.
- InvalidAudioError: The file cannot be decoded as valid audio.
- UploadFailedError: The upload cannot be completed.

## 5. Data

- file: File — the audio file selected by the user.
- mimeType: string — the detected audio format.
- durationSeconds: number — finite, nonnegative audio duration measured in seconds.
- audio: Blob — the audio content.
- status: "unpublished" — publication state of an accepted file.
- SUPPORTED_AUDIO_FORMATS: collection of permitted audio formats.
- MAX_CLIP_DURATION: configured maximum audio duration in seconds.


SUPPORTED_AUDIO_FORMATS: MP3, WAV, M4A (decision 4).
MAX_CLIP_DURATION: 60 seconds (decision 5).
Uploaded audio is stored temporarily in browser memory.


## 6. Rules

Preconditions:
- The user must select a readable audio file.
- The selected file must use a format included in SUPPORTED_AUDIO_FORMATS.

Postconditions:
- An accepted file is displayed as a playable, unpublished clip.
- A rejected file does not produce an accepted clip.

Invariant:
- Every accepted uploaded clip must have a permitted format and a duration less than or equal to MAX_CLIP_DURATION.

## 7. Edge Cases

1. The user selects an unsupported file format. Yappify rejects the file and displays an error.
2. The user selects an audio file exceeding MAX_CLIP_DURATION. Yappify rejects the file.
3. The user selects a corrupted audio file that cannot be decoded. Yappify displays an error rather than accepting it.
4. The user cancels file selection. No new clip is created.


## 8. Decisions and Open Questions

### Existing and Settled Decisions

The following implementation decisions were settled by the
team for Milestone 2.

1. Uploading and publishing are separate actions. An uploaded
   audio file remains unpublished until the user explicitly
   chooses to publish it.
   Source: Existing S-7 design document, Section 8.

2. Every accepted uploaded audio file must have a playback
   control so the user can listen to it.
   Source: Existing S-7 design document, Section 8.

3. Unsupported, corrupted, or invalid audio files must be
   rejected and must not create playable clips.
   Source: Existing S-7 design document, Sections 6 and 7.

4. SUPPORTED_AUDIO_FORMATS = MP3, WAV, and M4A.
   Only files in these formats can be accepted.
   Source: Team decision, 2026-11-19.
   Reason: These formats provide common audio compatibility
   while keeping the initial implementation manageable.

5. MAX_CLIP_DURATION = 60 seconds.
   Audio files exceeding 60 seconds must be rejected.
   Source: Team decision, 2026-11-19.
   Reason: Yappify focuses on short-form audio, and this
   limit keeps the initial feature small and testable.

6. Users must confirm that they own the uploaded audio or
   have the necessary rights or permission to use it.
   Uploading does not automatically publish the file.
   Source: Team decision, 2026-11-19.
   Reason: This establishes a basic upload policy while
   keeping publishing and moderation separate.

7. Accepted audio clips are stored temporarily in browser
   memory and are not guaranteed to survive a page refresh.
   Source: Team decision, 2026-11-19.
   Reason: Persistent storage is outside the initial S-7
   implementation and can be handled separately.

### Additional Decisions from Gap Check 2

8. Upload Architecture and Authentication

S-7 handles uploads entirely in the frontend: the selected
file is validated and held in browser memory, and no
request is sent to a backend. Authentication is not
implemented; a mock current-user record supplied by the
frontend data module stands in until a real auth backend
exists. The AGENTS.md persistence guidance is reconciled
with this frontend-only scope.

Source: Team decision, 2026-11-19.
Reason: M2 excludes a backend service, API, or database;
S-7 validates and previews in-browser behind one data
module a later backend can replace. Mock user data keeps
the upload path shaped for auth without inventing an
endpoint or a login flow.
Addresses: Q1, Q2, Q3, Q4.

9. Audio Format Validation

Supported formats are MP3, WAV, and M4A. The application
will check the file extension and MIME type, then attempt
to load the audio using the browser's audio capabilities.
Files with conflicting format information, unsupported
codecs, or undecodable content will be rejected.

The application will recognize common MIME variants:
- MP3: audio/mpeg, audio/mp3
- WAV: audio/wav, audio/x-wav, audio/wave
- M4A: audio/mp4, audio/x-m4a, audio/m4a

The returned mimeType will use a normalized value:
audio/mpeg, audio/wav, or audio/mp4.

Files with missing MIME types will undergo extension
validation and browser decoding. Audio-only MP4 files
with a .mp4 extension will not be accepted.

Source: Team decision, 2026-11-19.
Reason: Using browser validation provides a manageable
approach without implementing audio conversion.
Addresses: Q5, Q6, Q7, Q8, Q9, Q10, Q11.

10. Audio Duration Validation

The application will measure audio duration using HTML
audio metadata. Accepted clips must have a finite duration
greater than 0 seconds and less than or equal to 60 seconds.

Duration will not be rounded before validation.
A reported duration of 60.04 seconds will be rejected.
NaN, Infinity, and zero-second durations will be treated
as invalid audio.

Source: Team decision, 2026-11-19.
Reason: This provides a consistent, testable rule for
short-form audio uploads.
Addresses: Q12, Q13, Q14, Q15.

11. File Size and Upload Limits

The maximum file size will be 20 MB. Users can select
one audio file at a time.

Only one unpublished uploaded clip will be displayed.
A successful new upload replaces the previous clip.
A rejected upload leaves the previous valid clip unchanged.

While validation is running, the interface will display
a loading message and disable additional uploads.
A user may cancel the file picker without changing the
existing clip. Canceling selection will not call uploadAudio.

Source: Team decision, 2026-11-19.
Reason: These restrictions reduce memory usage and simplify
the first implementation.
Addresses: Q16, Q17, Q18, Q19, Q25.

12. Error Handling

Errors will be represented by TypeScript Error subclasses
exported from the upload module.

Validation will occur in this order:
1. Check file format.
2. Check file size.
3. Check whether the audio can be decoded.
4. Check the audio duration.

The first failed validation determines the error.

User-facing messages:
- UnsupportedFormatError:
  "Unsupported audio format. Please select MP3, WAV, or M4A."
- DurationLimitError:
  "Audio clips must be 60 seconds or shorter."
- InvalidAudioError:
  "This audio file could not be played or is invalid."
- UploadFailedError:
  "The audio file could not be loaded. Please try again."

Errors will appear below the upload control.
Unreadable files will produce UploadFailedError.
Files that cannot be decoded will produce InvalidAudioError.
UploadFailedError refers to local file loading rather
than a backend upload request.

A rejected file will not replace an existing valid clip.

Source: Team decision, 2026-11-19.
Reason: Consistent error behavior makes failures easier
to understand and test.
Addresses: Q20, Q21, Q22, Q23, Q24.

13. Copyright Confirmation

Before accepting an uploaded file, the user must check
a confirmation box containing the following statement:

"I confirm that I own this audio or have permission
to upload it."

The checkbox will be unchecked by default.
If the user does not confirm, the file will not be accepted.

The confirmation will be enforced in the frontend.
No permanent copyright-confirmation record will be stored
during S-7.

The existing uploadAudio interface will be revised to
accept a confirmation value, and a specific error will
be defined for missing confirmation.

Source: Team decision, 2026-11-19.
Reason: This makes the copyright requirement explicit
without implementing a complete moderation system.
Addresses: Q26, Q27, Q28, Q29.

14. Upload Result and Configuration

UploadResult.audio will contain the original selected
File without modifying or re-encoding it.

The interface will display the original filename and
duration. The frontend will create an object URL for
playback and revoke that URL when the clip is replaced
or removed.

The uploaded clip will retain the status "unpublished".
Publishing and status changes are outside S-7.

The implementation will reuse shared types or constants
from S-1 where compatible. Configuration values for
formats, duration, and file size will be stored in a
frontend constants module.

Source: Team decision, 2026-11-19.
Reason: Reusing the original file and shared configuration
reduces unnecessary processing and duplication.
Addresses: Q30, Q31, Q32, Q33, Q34.

15. User Interface and Accessibility

The upload control will appear alongside the existing
recording interface.

Users will select files through a standard file picker.
Drag-and-drop uploading is outside the S-7 scope.

The file picker will use an accept attribute for the
supported formats, but the application will still
validate each selected file.

An accepted clip will display:
- The original filename.
- The audio duration, displayed as `m:ss` (for example `0:05`).
- A native audio playback control.
- An unpublished status label.
- A button to remove the uploaded clip.

The file input and copyright checkbox will have
accessible labels. Error messages will be announced
through an accessible live region.

The feature will target current desktop versions of
Chrome, Firefox, Safari, and Edge, subject to supported
audio codecs.

Source: Team decision, 2026-11-19; amended 2026-11-19 to fix the
display format (supersedes the unqualified "The audio duration").
Reason: This keeps the interface straightforward while
providing basic accessibility and playback support. One
display format across the app: AC-6 fixes minutes and
seconds for the playback screen, and a clip under a minute
still reads correctly as `0:05`.
Addresses: Q35, Q36, Q37, Q38, Q39, Q40, Q41, Q42.

16. Testing Requirements

S-7 will use the existing Playwright test suite.
The main acceptance test will remain:

test_ac7_valid_audio_upload_displays_playback

Additional tests will cover unsupported formats,
duration violations, corrupted files, cancellation,
and copyright confirmation.

Test audio files will be small, locally generated
fixtures stored in the repository. Their origin and
usage rights will be documented.

A successful playback test will verify that the audio
player loads valid metadata and can begin playback,
rather than only checking that a player element exists.

The final implementation must use approved settings.

Source: Team decision, 2026-11-19.
Reason: These checks verify observable behavior and
the main edge cases identified in the design.
Addresses: Q43, Q44, Q45, Q46, Q47.
